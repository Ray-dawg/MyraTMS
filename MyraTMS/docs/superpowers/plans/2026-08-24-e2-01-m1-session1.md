# E2-01 M1 Session 1 — Shipper-Direct Gate Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the foundation for Engine 2's shipper-direct hard gate — schema, an FMCSA/SAFER/MTO authority-lookup client, a pure poster-classification function, a registry seed script, and a shadow-mode historical backfill — with **zero live-path changes**. Nothing in this plan touches `qualifier-worker.ts`, the Compiler, the Dispatcher, or any route that runs during a real pipeline drain.

**Architecture:** One additive migration creates three new tables (`poster_registry`, `authority_lookups`, `co_broker_agreements`) plus a poster-identity/classification column block on `pipeline_loads` and four review-routing columns on `exceptions`. `lib/verification/authority-lookup.ts` is a standalone external-lookup client (cache → FMCSA QCMobile → stubbed SAFER/MTO) with no worker dependency. `lib/pipeline/load-source-classifier.ts` holds the pure `classifyLoadSource()` decision function plus two DB-facing helpers (`findRegistryHit`, `findActiveAgreement`) that resolve its inputs. Two operator scripts (registry seed, historical backfill) compose these into runnable tools. All five pieces are independently testable and importable by Session 2 without modification.

**Tech Stack:** TypeScript, `@neondatabase/serverless` via `lib/pipeline/db-adapter.ts` (Pattern B — `db.query(text, params)`), Vitest against live Neon (matching existing `__tests__/pipeline/` convention — this codebase does not mock its database), `tsx` for script execution, native `fetch` with `AbortController` for the FMCSA HTTP client.

**Spec:**
- `Engine 2/E2-01_Engine2_Expansion_PRD.md` — full M1–M6 design (§4 is the section this plan implements: §4.3 authority-lookup, §4.4 registry, §4.5 decision table, §4.9 reason codes, §4.10 data model, §4.11 config, §4.12 test plan)
- `MyraTMS/docs/superpowers/specs/2026-08-24-e2-01-m1-session1-design.md` — the two reconciliation decisions this plan applies (co_broker_agreements shape, FMCSA webKey deferral) and the exact Session 1 scope boundary

## Global Constraints

- **Zero live-path changes.** No file under `lib/workers/`, `lib/pipeline/negotiation-brief.ts`, `lib/pipeline/compliance-service.ts`, or any `app/api/**` route is modified in this plan. If a task appears to need one, stop — it belongs in Session 2+.
- **Migrations are additive and idempotent.** Every `CREATE TABLE` uses `IF NOT EXISTS`, every `ALTER TABLE ... ADD COLUMN` uses `IF NOT EXISTS`, every `CREATE INDEX` uses `IF NOT EXISTS`. Never edit a shipped migration's `CREATE TABLE` block — add a new migration instead (per `Engine 2/CLAUDE.md`).
- **`co_broker_agreements` uses T-19's shape**, not the PRD's literal text: `tenant_id BIGINT NOT NULL REFERENCES tenants(id) ON DELETE CASCADE`, no default. Never `tenant_id INTEGER DEFAULT 1` — see design doc §2.
- **Fail closed, always.** Every ambiguous, errored, timed-out, or not-implemented path in the lookup client and the classifier must resolve toward `'unresolved'`/`'error'`/review — never toward an accept. This is tested explicitly, not just asserted in comments.
- **SAFER (Playwright) and Ontario MTO (Playwright) providers are stubbed in this session.** MyraTMS has no Playwright dependency (confirmed: `grep playwright package.json` → no match); Playwright browser-pool infrastructure lives only in the sibling `scraper/` project. Building that infrastructure into MyraTMS is a separate, real decision deferred past Session 1. The stubs return `status: 'error'` immediately and still write an `authority_lookups` audit row (reason `not_implemented`) — this fails closed by construction (an `'error'` status routes to review at classification time, never to accept), so Session 1 ships PRD-correct behavior without needing a browser pool.
- **Path alias:** `@/*` → MyraTMS project root. Use it in all new files (`@/lib/pipeline/db-adapter`, `@/lib/verification/authority-lookup`, etc.).
- **DB access:** Pattern B only (`import { db } from '@/lib/pipeline/db-adapter'`, then `db.query<T>(text, params)`) — this is what every pipeline file uses; Pattern A (`neon()` tagged templates) is for TMS API routes, not this code.
- **Tests hit live Neon**, matching `__tests__/pipeline/dispatcher-prospect-gate.test.ts`'s convention: seed fixture rows with a `TEST_`/timestamp-suffixed identifier in `beforeAll`, clean up in `afterAll`, no mocking of the database.
- **No new npm dependencies.** Everything in this plan is buildable with what's already in `package.json` (`zod`, `@neondatabase/serverless`, native `fetch`, `vitest`, `tsx`).
