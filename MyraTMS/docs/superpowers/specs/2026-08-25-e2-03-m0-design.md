## Three gaps found auditing the existing draft against the live system

### 1. Migration 041 assumed E2-01's 040 had already landed on master — fixed

`041`'s original header comment said the `exceptions` table's `pipeline_load_id`/`source_module`/`suggested_action`/`sla_due_at` columns "already carr[y]... via `040_shipper_direct_gate.sql` (already in the repo)" and don't need repeating. **Master does not have 040** — E2-01 is still on its own unmerged branch. Checked the live `exceptions` table directly (`information_schema.columns`) and found those four columns already present on the actual shared Neon database (E2-01's Task 1 implementer applied `040` for real against `DATABASE_URL`, independent of git branch state — there's one shared database, not per-branch databases). So the *live* dependency is already satisfied today, but the *migration file* would be broken on a fresh database or a Neon verification branch that doesn't yet have `040`'s history.

**Fix (already applied, commit pending):** `041` now adds those four `exceptions` columns itself via the identical `ADD COLUMN IF NOT EXISTS` DDL, order-independent of `040`, mirroring the exact reconciliation pattern E2-01 itself used for `co_broker_agreements` against T-19's migration `035`. Verify script updated to check for them (5th check, was 4).

### 2. The Alert Center won't show useful context for an M0 escalation as originally assumed — resolved, no new UI work needed

PRD §5.2 says M0's escalation "reuses the escalation path that already exists for the prospect gate... same table, same UI... nothing new to build here." Checked the actual prospect-gate escalation (`dispatcher-worker.ts`'s `escalateProspect()`, lines 186–201) and found it does **not** insert into `exceptions` at all — it only sets `pipeline_loads.stage = 'escalated'` and logs. So "the existing path" doesn't populate the Alert Center today; M0 is the first thing that will actually write a carrier-related `exceptions` row.

Checked `app/api/exceptions/route.ts`: its `GET` query `LEFT JOIN`s `loads l ON e.load_id = l.id` and `carriers c ON e.carrier_id = c.id` for display context (`reference_number`, `origin_city`, `dest_city`, `carrier_name`). M0's escalation fires **before** `createTMSLoad()` ever runs — there is no `loads` row yet, so `load_id` would be `NULL` and the load-context columns would come back empty via the existing query. `carrier_id` **does** resolve correctly, though (`top_carrier_id` is a real `carriers.id`).

Checked the actual live `exceptions` table schema directly (not just the route's SELECT) and the actual Alert Center component (`components/alert-center.tsx`): it renders `exc.title` and `exc.detail` as free text, plus `severity` and (optional) `carrier_name`. Both `title` and `detail` are plain columns already on the table.

**Resolution: no new UI or API-route work needed.** The escalation insert sets `carrier_id = top_carrier_id` (so `carrier_name` resolves via the existing join) and puts everything a human needs to act — origin, destination, pickup date, equipment, `top_carrier_id`, and the "AI carrier calling is not yet live" framing — directly into `title`/`detail`, in addition to the structured `pipeline_load_id`/`source_module`/`suggested_action` columns for future consumers (T-24's fuller console, when it's built). This satisfies PRD acceptance criterion 2 ("evidence a human needs... without opening the TMS load record separately") using only existing, already-rendered columns.

### 3. `AUTO_BOOK_PROFIT_THRESHOLD` cleanup is half-done — the other half is exactly E2-03's fix #3

Found that T-18/T-19 (Engine 3, already merged to master) already retired this variable at the config/decision level: `.env.example:72` reads `# AUTO_BOOK_PROFIT_THRESHOLD removed (T-19): never read by any decision path`, and `getMarginFloor()` (`lib/tenants/margin-floor.ts`) is the real mechanism now. But four operational files were never updated and still read/reference the retired variable as if it's live:
- `scripts/run-workers.ts:92` (kill-switch status log)
- `scripts/sprint6-shadow/01-preflight.ts:53,73` (preflight check)
- `scripts/sprint6-shadow/05-live-call-preflight.ts:77-81` (live-call gate — this one actually **blocks or passes a real go-live decision** based on a variable the system no longer reads)
- `scripts/sprint6-shadow/README.md:44,136` (operator runbook)

This is precisely E2-02 §4 item 9 / E2-03 §5.4.3's finding, confirmed exactly as described: "An operator following the runbook today believes they're gating auto-book with a variable the system no longer reads." Fix: update all four to note the variable is retired (T-18/T-19) and point at the real mechanism (`authority_envelopes` / `getMarginFloor()`), per PRD §5.4.3's instruction — documentation/tooling fix, not a decision-path code change (the variable was already inert; this doesn't change behavior, only honesty).

## M0 implementation, precisely

**Behavior change (`dispatcher-worker.ts`):** the branch at lines 118–164 (fetchCarrierRate → createTMSLoad → assign → tracking link) only runs when `CARRIER_AUTO_ASSIGN_ENABLED=true`. When `false` (the default), it instead writes a `carrier_needed`-style hold: `pipeline_loads.stage = 'escalated'` (matching `escalateProspect()`'s existing pattern) plus a new `exceptions` insert (see gap #2) with `source_module = 'carrier_confirmation_required'`.

**Idempotency guard:** before `createTMSLoad()` runs (only reachable when the flag is `true`), check `pipeline_loads.tms_load_id IS NOT NULL`; if set, skip creation and resume from `assignCarrier()` using the existing `tms_load_id`. `fetchPipelineLoad()`'s `SELECT` needs `tms_load_id` added to its column list to support this check.

**Zero-rate honesty flag:** `fetchCarrierRate()`'s fallback branch (`return ... : 0`) is where `carrier_cost_estimated` becomes `true`; threaded through `createTMSLoad()`'s body so the TMS `loads` row is written with it set correctly at creation time (column added by `041` on `loads`, default `false`).

**Flag:** `CARRIER_AUTO_ASSIGN_ENABLED`, default `false` — the one flag in this whole arc that defaults OFF (§5.3), because the dangerous state is the current always-on behavior, not the guarded one.
